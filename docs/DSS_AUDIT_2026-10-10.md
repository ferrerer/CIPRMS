### Worked numerical example (live data, from this session's test fixtures)

Dataset filtered to `country=Testland` (3 records): 1 Active, 1 Expired, 1 Expiring Soon (30 days out).

- Custom Report Builder, `reportType=By Country` → group "Testland": `Active=1, Expiring Soon=1, Inactive=1, Total=3` → `1+1+1=3` ✓ (metric #3, three-way breakdown)
- Custom Report Builder, `reportType=Active vs Inactive`, `compareBy=Country` → group "Testland" **after today's fix**: `Active=1, Inactive=2, Total=3` → `1+2=3` ✓ (metric #3, two-way breakdown, Expiring Soon folded into Inactive)
- Comparison feature, `compType=Active vs Inactive`, same filter: `totalA=1, totalB=2` — now identical to the Custom Report Builder's own "Active vs Inactive" grouped-by-Country result for the same filtered data.
- `% of Total` for the Testland group in a `By Country` report with no other countries present: `3/3×100 = 100.0%` ✓

## 3. Finding #1 (CONFIRMED BUG, FIXED): "Inactive" meant two different things for the same filtered data

**Symptom:** For the SAME filtered dataset, `reportType=Active vs Inactive` run through the Custom Report
Builder's grouped-report path (`computeCustomReportData`) and the dedicated Comparison feature's own
`compType=Active vs Inactive` (`computeComparisonReport`) returned **different "Inactive" counts**, and the
Custom Report Builder's own `Active + Inactive` columns did not sum to `Total` whenever a group contained an
"Expiring Soon" record.

**Root cause:** `computeComparisonReport`'s `matchStatus()` (`cirl.js:4915`) already folds Expiring Soon into
Inactive: `status==='Expired' || status==='Inactive' || status==='Expiring Soon'`. But
`computeCustomReportData`'s per-metric matcher used a 2-way definition for the *same* word:
`status==='Expired' || status==='Inactive'` (Expiring Soon excluded) — for the plain `['Active','Inactive']`
metric shape used by `reportType=Active vs Inactive`. A prior fix session (visible in the pre-existing test
comment at `test/reports.test.js:286-291`) already identified and fixed this exact "Expiring Soon counted in
Total but in neither displayed column" defect for the six **"By [Dimension]"** report types, but explicitly
left `Active vs Inactive` untouched — so the inconsistency the brief asked me to check for ("the same metric
has consistent definitions between Custom Report Builder and Comparison") was still live.

**Why a blanket fix would have been wrong:** the six "By [Dimension]" types already track Expiring Soon as
its own column (`['Active','Expiring Soon','Inactive']`); folding it into Inactive there too would have
double-counted it and broken the reconciliation those types already have correctly.

**Fix applied** (`cirl.js`, inside `computeCustomReportData`'s per-group metric loop):

```js
const inactiveHasNoOtherBucket = !metricGroups.includes('Expiring Soon') && !metricGroups.includes('Expired');
// ...
else if (m === 'Inactive') match = (p.status === 'Expired' || p.status === 'Inactive' || (inactiveHasNoOtherBucket && p.status === 'Expiring Soon'));
```

Folds Expiring Soon into Inactive **only** when nothing else in that report's metric set already accounts for
it — which today is exactly the plain `['Active','Inactive']` shape used by `reportType=Active vs Inactive`.
The six "By [Dimension]" types, and the `'Custom Comparison'` bare-default fallback (see Finding #2), are
untouched.

**Tests** (`test/reports.test.js`, TDD — written failing first, confirmed failing against the pre-fix code,
then confirmed passing after the fix):
- `Active vs Inactive: Active + Inactive reconciles to Total (Expiring Soon folded into Inactive)`
- `Active vs Inactive: Custom Report Builder and the dedicated Comparison feature now agree on what counts as Inactive`
- `"By [Dimension]" types are unaffected: Inactive still excludes Expiring Soon (it has its own column)` — regression guard for the untouched six types

Full suite result (`test/reports.test.js`, `test/custom-report-builder-completion.test.js`,
`test/report-type-status-dependency.test.js`, `test/custom-report-country-search.test.js`): **200 passed, 1
pre-existing failure unrelated to this fix** (see Finding #4).

## 4. Finding #2 (latent, NOT fixed — flagged only): `Custom Comparison`'s bare default double-counts Expired

When `reportType=Custom Comparison` is selected with no `customStatuses` supplied, `metricGroups` defaults to
`['Active','Inactive','Expired']` (`cirl.js:3940`). Since `Inactive` already matches `status==='Expired'`,
every Expired record is counted in **both** the `Inactive` and `Expired` columns — `Active+Inactive+Expired`
sums to *more* than `Total`. This predates today's session and is unrelated to Finding #1's fix (confirmed by
not touching this path at all: my conditional only activates when neither `'Expiring Soon'` nor `'Expired'` is
already a separate column, which is false here).

I did not fix this because: (a) it appears unreachable from the actual UI — the Custom Comparison form
always submits explicit `customStatuses` — so it's dead-code-shaped rather than a live user-facing defect, and
(b) deciding whether the *intended* default should be `['Active','Inactive']`, `['Active','Expired']`, or
something else is a product decision, not something to guess at silently. **Recommend:** either remove the
unreachable default (require `customStatuses`) or make it `['Active', 'Expired', 'Expiring Soon']` (three
genuinely disjoint statuses, no overlap) if a true default is wanted.

## 5. Finding #3 (proposed enhancement — clearly NOT an existing capability)

The Comparison feature's `diff` is an absolute record-count difference only (`|totalA − totalB|`). The brief's
own worked example ("Percentage difference: (A − B) / B × 100, only when B is nonzero and explicitly defined
as the baseline") is **not implemented anywhere** in this codebase today. **Proposed, not built:** add
`diffPercentage = totalB > 0 ? ((totalA − totalB) / totalB × 100) : null` to `computeComparisonReport`'s return
value, with Group B UI-labeled as "baseline" so the direction of the percentage is unambiguous, and `null`
(rendered as "N/A", not `0%` or `Infinity`) when the baseline group is empty. Useful for CIRL decision-making
because an absolute difference of "12" means something very different when the baseline is 5 versus 500; a
percentage makes magnitude comparable across report runs. Needs: no new DB field, just one derived number in
the existing response.

## 6. Finding #4 (pre-existing, unrelated failure — flagged, not changed)

`test/reports.test.js` → `"An explicit Status filter overrides the Report Type's implied status"` expects an
explicit `status=Expired` to win over `reportType=Active Partnerships`'s implied status. The actual code
(`cirl.js:3864-3872`) does the opposite **by design**, per its own comment: for any status-typed Report Type,
"the implied status is AUTHORITATIVE... ignored so it can never create a contradictory result" (a documented
2026-09 security/consistency hardening decision, not an accident).

**Confirmed pre-existing**, not caused by today's changes: reproduced identically with `git stash` reverting
every edit from this session, then reverted the stash back. This is a genuine test/code mismatch worth fixing,
but it's outside today's requested scope (Comparison/Custom Report Builder formula consistency) and changing a
documented security-hardening behavior isn't something to do silently — flagging for a decision: either the
test is stale and should be updated to assert the current (intentional) contract, or the override behavior was
wanted back and the implementation should change instead.

## 8. Edge cases checked against source (brief section 6)

| Edge case | Where handled | Verdict |
|---|---|---|
| Zero denominator | `row.Total > 0 ? … : '0.0'` (metric #4), `docs.length > 0 ? … : '0.0'` (metric #5), `grandTotal > 0 ? … : 0` (metric #7), `targetCount > 0 ? … : 0` (metric #8) | Guarded everywhere a division occurs |
| Missing target | `targetCount` is a required positive integer at creation (`validateTargetInput`); a target simply doesn't exist for a period with none created | No divide-by-missing-target path exists |
| Empty dataset | `comparisonData` is `[]`, `totalRecords`/`totalA`/`totalB` are `0` — confirmed by existing test `"By Institution, filtered to a country with zero matches: zero-result behavior is unaffected"` | Handled, tested |
| Date boundaries | `filterByDateRange` (`cirl.js:3112`) rejects only strictly-outside dates (`<`/`>`), so a boundary-equal date is included (inclusive range) | Correct, inclusive |
| Duplicate partnership records | Not deduplicated by Comparison/CRB — each stored document counts once by design; there is no "same partnership entered twice" detection in the reporting layer (distinct from the unrelated OCR upload pipeline's own SHA-256 duplicate-file check) | By design, not a bug — flagging only so it's an explicit, documented choice rather than an unexamined gap |
| Inactive/expired partnerships | `computeStatusFromEnd` recomputes status fresh from `end` on every single report run (`cirl.js:6359`) — never trusts a possibly-stale stored `status` field | Correct |
| Different partnership statuses | Active / Expiring Soon / Expired / Renewed / Non-Renewed all independently matchable via `metricGroups`/`matchStatus` | Correct, see Finding #1 for the one inconsistency found and fixed |
